====================================================
01. CORRECTED ABSTRACT
====================================================

AI coding assistants like Claude Code, Cursor, and Copilot have changed how
we write code -- but until recently, they couldn't securely touch or manage
our cloud infrastructure. Giving an AI agent access to AWS APIs usually
meant exposing highly privileged credentials to a local workspace, or
risking multi-step hallucinations with no guardrails.

Enter the Model Context Protocol (MCP). In this technical, demo-driven
session, we break down how to design, code, and productionize a custom
AWS-native MCP server. You'll see the move from a brittle local prototype
to a secure, enterprise-ready cloud architecture -- built on the Streamable
HTTP transport that replaced MCP's earlier stdio/SSE model, so your tools
can run stateless, horizontally, inside your AWS perimeter.

We close by looking at where the protocol itself is going: the Skills Over
MCP effort, and how a 2026 debate about what belongs in the protocol
(SEP-2076) turned into a shipped extension (SEP-2640).

02. WHAT THE AUDIENCE WALKS AWAY WITH
====================================================

- The MCP blueprint. How MCP bridges LLM reasoning and live AWS API calls --
  tools, resources, and why that split exists.

- Building from scratch. A custom MCP server in Python with FastMCP,
  exposing live AWS diagnostics as tools.

- Stateless scaling on AWS. Why Streamable HTTP (post SEP-2575/2567) is
  what makes ECS Fargate + ALB horizontal scaling possible for MCP, where
  SSE-session servers couldn't.

- Zero-trust guardrails. Least-privilege via IAM task roles -- no long-lived
  credentials baked into the container.

- Enterprise Control. Connecting a cloud-hosted MCP server to local IDEs
  (Cursor, Claude Desktop) over a real, working OAuth 2.1 flow (Cognito as
  the Authorization Server) -- then watching it happen live via a
  no-terminal web app, before touching the ADFS/Okta/IAM Identity Center
  enterprise-IdP story as a one-line provider swap.

- Where the spec is headed. Skills over MCP -- SEP-2076's open question,
  resolved as the Final SEP-2640 Skills Extension.

04. DEMO ARCHITECTURE -- DOABLE ON ONE AWS ACCOUNT
====================================================

Everything below is standard, well-documented AWS building blocks. No
custom infra needed beyond what's listed.

  Claude Desktop / Cursor   (Remote MCP config, OAuth bearer token)
            |
            v
  Application Load Balancer (TLS termination, routes to ECS service)
            |
            v
  ECS Fargate task          (FastMCP server, Streamable HTTP, stateless)
            |
            v
  IAM task role             (Least-privilege: e.g. read-only
                              CloudWatch/EC2 describe)
            |
            v
  AWS APIs                  (The actual diagnostics being surfaced as
                              tools)

AUTH NOTE
For the live demo, terminate OAuth at a Cognito User Pool (or an ALB OIDC
listener) issuing short-lived tokens to the MCP client -- this is enough to
demonstrate the real OAuth 2.1 flow MCP clients expect (SEP-990). Enterprise
IdPs like ADFS, Okta, or Azure AD would federate into Cognito the same way
in production; that federation step is a one-line mention on the slide, not
something to stand up live.

CONTAINER PATH
Write the FastMCP server -> build & push to ECR -> `ecs create-service`
with the task role attached -> register target group behind the ALB. All
scriptable with the CLI or CDK ahead of the talk; the "build" segment on
stage only adds one new tool to an already-running server.

MAIN HANDS-ON PATH: THE LAUNCHER, VIA BUILDER WEB
launcher/ ("MCP Builder") is a second always-on FastMCP server -- same
Cognito pool via Dynamic Client Registration -- whose one tool,
submit_server, does the CONTAINER PATH above programmatically via boto3
the moment an attendee submits code. At 00:37 that's fronted by
builder-web/, a browser app: describe a tool in plain English, "Draft
with AI" turns it into reviewable code, click Deploy. No terminal, no
IDE. Each submission gets its own ECS task + its own free CloudFront
domain (needed because Cognito's OAuth callback list is exact-match, no
wildcards -- one shared domain can't serve multiple logins). Submitted
code is AST-validated against an import allowlist (random/math/
datetime/json/re only, no file/network/subprocess) before anything
touches AWS. This is the "zero-trust guardrails" bullet made concrete a
second time, from the opposite direction: least-privilege on the
INFRASTRUCTURE side (section 05's IAM task role) plus validation on the
CODE side (what actually gets allowed to run on that infrastructure).

STRETCH GOAL: SAME submit_server, THREE MORE WAYS IN
For attendees who want to see the code underneath the web app: call
submit_server directly from MCP Inspector (most direct); clone
kickstart/, write a real FastMCP tool, run `python submit.py "name"`
(the hand-written path, same markers the web app's AI draft also
produces); or describe it in chat to the Electron demo agent, which
drafts and deploys with a human approval click before anything ships
(no IDE at all). Project the resulting URLs in MCP Inspector on the
shared screen as they land.

05. ENTERPRISE CONTROL, EXPLAINED
====================================================

This was the unclear bullet in the original outline. Here's the corrected,
concrete version:

THE PROBLEM
Once your MCP server is remote (on ECS, not on localhost), the local IDE --
Claude Desktop, Cursor -- needs a way to authenticate to it that isn't
"paste a static API key into a config file."

THE MECHANISM
MCP's remote auth model is OAuth 2.1. The client does a standard
authorization-code + PKCE flow, gets a short-lived token, and sends it as a
bearer token on every request. SEP-990 (Final) specifically adds support
for enterprise IdP policy controls inside that flow -- conditional access,
MFA enforcement, that kind of thing.

STATUS: THIS IS NOW A REAL, WORKING BUILD -- NOT JUST A SLIDE
Updated from the original plan. There are two real OAuth-protected FastMCP
servers in this repo now, BOTH pointed at the SAME Cognito User Pool
(consolidated from an earlier two-pool design -- one pool, one app client,
self-signup left open for everyone, plus a dedicated admin-created login
for the speaker). Both use FastMCP's built-in AWSCognitoProvider (a
Cognito-specific OAuth proxy -- Cognito has no native Dynamic Client
Registration, so the provider fakes RFC 7591 on top of one pre-registered
app client):

  server/finance_mcp_server.py   Speaker's own reference demo (the one
                                  built live in the 00:21 segment). Logs
                                  in with the dedicated test user that
                                  infra/setup_cognito.py creates.

  kickstart/server_template.py   Now the hand-written stretch-goal path
                                  at 00:37 (MCP Builder Web is the main
                                  flow). Same auth wiring, same pool,
                                  generic placeholder tool (`ping`). Each
                                  attendee clicks "Sign up" on Hosted UI
                                  to create their own login, no AWS
                                  account needed -- see
                                  kickstart/README.md.

  Torn down cleanly afterward with infra/teardown_cognito.py (one pool,
  one teardown).

WHERE ADFS/IAM FIT
ADFS speaks SAML, not OAuth, so in a real enterprise it sits one layer
back -- federated into something OAuth-native (Cognito User Pool, or an
OIDC-capable IdP) which is what actually issues the token the MCP client
holds. IAM Identity Center is the AWS-native alternative to that same
pattern. For the talk: name-check ADFS/IAM Identity Center as "this is
where your corporate identity plugs in," and use the Cognito-vs-Okta
swap (one provider class, same FastMCP server) as the concrete proof --
no need to stand up a federation trust live.

06. CLOSING: SKILLS OVER MCP
====================================================

The protocol's own "what's next" story -- a real, recently-resolved debate,
good closer material.

2026-02-01  IG formed
            Experimental Skills-over-MCP repo created. Native skills
            support in host apps shows demand; question raised: does MCP
            need a first-class "skill" primitive, or do existing
            primitives (resources, prompts) already cover it?

[Draft]     SEP-2076 -- "Agent Skills as a First-Class MCP Primitive"
            The PR that framed the open question. Spawned the Skills Over
            MCP Working Group (Anthropic, AWS, Google, Bloomberg,
            Databricks, GitHub, and others at the table).

[Final]     SEP-2640 -- Skills Extension, merged 2026-09-13
            The answer: a Resources-based extension
            (io.modelcontextprotocol/skills). Skills stay lightweight --
            no server, no auth, no runtime -- but can now be discovered
            and distributed THROUGH an MCP server, instead of competing
            with it.

One-sentence version for the slide:
  "Knowledge is a Skill, connectivity is MCP" -- and Skills-over-MCP is the
  bridge that lets a skill travel inside the same channel your tools
  already use.
