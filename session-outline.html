00 What I corrected in talk.txt

Three factual fixes, each backed by a real, finalized MCP spec change — worth citing on slides since they make the technical claims verifiable.

Transport
"Moving beyond basic WebSockets"
MCP never standardized on WebSockets. The real lineage is stdio → HTTP+SSE → Streamable HTTP.
Why it matters: Final SEP-2575 "Make MCP Stateless" and SEP-2567 "Sessionless MCP via Explicit State Handles" are the actual specs behind your stateless-ECS story — cite the SEP numbers instead of the WebSocket line.
Closing topic
"End with SEP-2076"
SEP-2076 ("Agent Skills as a First-Class MCP Primitive") was the question — it spawned the Skills Over MCP Working Group. The answer is SEP-2640, the Skills Extension, which went Final 2026-09-13.
Frame the close as "the debate that became a shipped spec": 2076 → 2640.
Enterprise Control
Undefined bullet, no mechanism named
This is OAuth 2.1 remote auth for MCP clients, with enterprise IdP policy support. SEP-990 (Final) is the actual spec.

01 Corrected abstract

AI coding assistants like Claude Code, Cursor, and Copilot have changed how we write code — but until recently, they couldn't securely touch or manage our cloud infrastructure. Giving an AI agent access to AWS APIs usually meant exposing highly privileged credentials to a local workspace, or risking multi-step hallucinations with no guardrails.

Enter the Model Context Protocol (MCP). In this technical, demo-driven session, we break down how to design, code, and productionize a custom AWS-native MCP server. You'll see the move from a brittle local prototype to a secure, enterprise-ready cloud architecture — built on the Streamable HTTP transport that replaced MCP's earlier stdio/SSE model, so your tools can run stateless, horizontally, inside your AWS perimeter.

We close by looking at where the protocol itself is going: the Skills Over MCP effort, and how a 2026 debate about what belongs in the protocol (SEP-2076) turned into a shipped extension (SEP-2640).

Auth note For the live demo, terminate OAuth at Cognito User Pool (or an ALB OIDC listener) issuing short-lived tokens to the MCP client — this is enough to demonstrate the real OAuth 2.1 flow MCP clients expect (SEP-990). 05 Enterprise Control, explained

This was the unclear bullet in the original outline. Here's the corrected, concrete version:

The problem: once your MCP server is remote (on ECS, not on localhost), the local IDE — Claude Desktop, Cursor — needs a way to authenticate to it that isn't "paste a static API key into a config file."

The mechanism: MCP's remote auth model is OAuth 2.1. The client does a standard authorization-code flow, gets a short-lived token, and sends it as a bearer token on every request to the ALB. SEP-990 (Final) specifically adds support for enterprise IdP policy controls inside that flow — conditional access, MFA enforcement, that kind of thing.

Where ADFS/IAM fit: ADFS speaks SAML, not OAuth, so in a real enterprise it sits one layer back — federated into something OAuth-native (Cognito User Pool, or an OIDC-capable IdP) which is what actually issues the token the MCP client holds. IAM Identity Center is the AWS-native alternative to that same pattern. For the talk: name-check ADFS/IAM Identity Center as "this is where your corporate identity plugs in," and use the Cognito-vs-Okta provider swap as the concrete proof — no need to stand up a federation trust live.

Status: real build, not just a slide Two working OAuth-protected FastMCP servers now exist in this repo, both pointed at the same Cognito User Pool (consolidated from an earlier two-pool design) via FastMCP's built-in AWSCognitoProvider (a Cognito-specific OAuth proxy — Cognito has no native Dynamic Client Registration, so it fakes RFC 7591 on top of one pre-registered app client). server/finance_mcp_server.py is the speaker's own reference demo, logging in with a dedicated admin-created test user; kickstart/server_template.py is what attendees run themselves at 00:33, self-signing-up their own Hosted UI login on that same pool. One pool, one teardown with infra/teardown_cognito.py.

06 Closing: Skills over MCP

The protocol's own "what's next" story — a real, recently-resolved debate, good closer material.

2026-02-01IG formed
Experimental Skills-over-MCP repo created
Native skills support in host apps shows demand; question raised: does MCP need a first-class "skill" primitive, or do existing primitives (resources, prompts) already cover it?
DraftSEP-2076
"Agent Skills as a First-Class MCP Primitive"
The PR that framed the open question. Spawned the Skills Over MCP Working Group (Anthropic, AWS, Google, Bloomberg, Databricks, GitHub, and others at the table).
FinalSEP-2640
Skills Extension — merged 2026-09-13
The answer: a Resources-based extension (io.modelcontextprotocol/skills). Skills stay lightweight — no server, no auth, no runtime — but can now be discovered and distributed through an MCP server, instead of competing with it.

The one-sentence version for the slide: knowledge is a Skill, connectivity is MCP — and Skills-over-MCP is the bridge that lets a skill travel inside the same channel your tools already use.
