"Just give the agent an access key."

  • That's how most people start giving an AI coding agent access to cloud infrastructure. A static key, pasted into a config file, full account permissions.
  • It breaks down fast. No scoping, no audit trail, no revocation without rotating the key everywhere it's used.
  • The real risk isn't malice — it's a multi-step hallucination with no guardrails between "the agent decided to" and "it actually happened in production."
Hook: ask the room "who's pasted an API key into a Claude Desktop config?" Get a laugh/nod, then pivot — that's the exact problem this talk solves.

The MCP blueprint

TOOLS Actions the agent can invoke — get_quote(), not just read data
+
RESOURCES Context the agent can read — files, API responses, state
+
PROMPTS Reusable instruction templates the host can surface

One client–server handshake, three primitives. Part 2 is entirely "how do we run the server half of that handshake safely, in AWS" — nothing here is AWS-specific.

A fourth, Skills, has since joined the spec — more on that at the close.

You don't have to build every server

Before we build one: the command in .mcp.json just tells the client how to launch it, and a whole marketplace already exists.

uv run script.py Your own local script — inline PEP 723 metadata declares its deps, uv installs them into an ephemeral env on first run
uvx mcp-server-fetch Official, published MCP servers, run by package name — the npx of this ecosystem. Fetch, git, SQLite, and more already exist
uvx awslabs.aws-documentation-mcp-server AWS Labs ships official MCP servers too — live AWS docs, CDK guidance, cost analysis, zero infrastructure of your own

So when's it worth building your own? When you need a tool over data or an API nobody's published yet — your own database, your own internal service. That's everything else in this talk.

npx @modelcontextprotocol/inspector --config .mcp.json — no --server flag, and Inspector loads every entry in the file into one UI with a dropdown to switch between them.

Demo if time: add mcp-server-fetch to .mcp.json live, ask the agent to fetch a page. C3 00:13 · 2 min

Two shapes of MCP server

stdio
The client launches your script as a subprocess and talks over stdin/stdout. No network, no auth handshake — trust comes from "you're the one who launched it."
your laptop only
Streamable HTTP
A real network service, reachable by any client that has the URL. Needs real auth — this is what Part 2 builds.
anyone, anywhere

Part 2 builds the second kind. But stdio is the right call whenever a tool needs your local filesystem, your git repo, or secrets that should never be reachable from the internet in the first place.

Quick framing beat, don't over-dwell. Good concrete stdio example if asked: a tool scoped to read/write files in one sandboxed local folder — zero network exposure by construction, not by policy.
C4 00:15 · 3 min

How a server advertises what it has

1 @mcp.tool / @mcp.resource / @mcp.prompt register into an in‑memory registry, at startup or any time after
↓
2 Client sends tools/list, resources/list, prompts/list over that same connection
↓
3 Server answers from whatever's registered right now — there's no separate discovery service

No magic: a typed signature becomes the JSON Schema, the docstring becomes the description. Worth remembering for Part 2 — that registry lives in process memory, which means it's also exactly what a restart wipes clean.

Deliberate setup for the Part 2 war story slide — plant the "in-memory, wiped on restart" detail here so it pays off later instead of landing as a surprise non-sequitur.
C4.5 00:18 · 3 min

The protocol, method by method

  • initialize → notifications/initialized opens the session — protocol version and capabilities get negotiated, then the client confirms it's ready
  • tools/list / tools/call discover what's registered, then invoke one by name with arguments
  • resources & prompts follow the same shape resources/list+read, prompts/list+get — same list-then-fetch pattern, different payload
  • notifications/tools/list_changed server-initiated push when its registry changes — the client re-lists instead of guessing
// what tools/call actually looks like on the wire
{"method": "tools/call", "params": {"name": "get_quote", "arguments": {"ticker": "AMZN"}}}
// server replies with content blocks, not a bare return value
{"result": {"content": [{"type": "text", "text": "AMZN: $231.40"}], "isError": false}}

Plain JSON‑RPC 2.0, over whichever transport C3 covered — four method families whether you're asking for tools, resources, or prompts.

Source: modelcontextprotocol.io/specification/2025-06-18. If asked about resources/subscribe or completions, those are optional capabilities beyond this baseline — mention briefly, don't dive in.

D3 optional · time‑permitting

War story: the OAuth client that vanished

// MCP Inspector, re-connecting to a server I'd already authed against last night
Client Not Registered
// The client ID 248ccdc4-... was not found in the server's client registry.
1 Inspector calls /register, caches the client ID it gets back — forever, in a local file
↓
2 I redeploy the server; its in‑memory client registry (the one from Part 1, slide C4) resets to empty
↓
3 Inspector reuses the cached (now‑dead) ID instead of re‑registering — auth fails

Client-side state outlived server-side state across a restart. If you build an OAuth-protected MCP server, your dynamic client registrations need to live somewhere durable — not just in-process memory — or every client that registered before your last deploy has to start over.

Real bug, hit it building this exact deck's demo server the night before. Good live moment if time allows: show the error page, then find+delete the stale entry in ~/.mcp-inspector/storage/oauth.json, reconnect, watch it re-register clean. Cut this slide first if running long — it's a bonus, not load-bearing.

CLOSING 00:55 · 4 min

Closing: Skills over MCP

2026-02-01 · working group formed → SEP-2076 (draft) → SEP-2640 · Final, 2026-09-13
  • The question: does MCP need a first-class "skill" primitive, or do resources/prompts already cover it?
  • The answer: a Resources-based extension. Skills stay lightweight — no server, no auth, no runtime — but travel through the same MCP channel your tools already use.
  • No new verbs. Skills ride on resources/list and resources/read — same list-then-fetch pattern from C4.5, now also carrying skill definitions tagged by kind. That reuse is the point.

"Knowledge is a Skill, connectivity is MCP."

A real, recently-resolved debate — good closer because it's not hypothetical, it shipped three months before this talk.
